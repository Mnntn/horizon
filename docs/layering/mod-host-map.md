# The mod host above the engine: the map (#2534)

Every place an engine crate touches a mod crate, grouped by strand, with the move or socket each strand needs. The
tables between the markers below are generated by `tools/layering/scan_engine_mod_edges.py --map`, which
runs from the repository root, reads `cargo metadata` and the sources, and compiles nothing. `--json FILE` writes
every edge (file, line, kind, path, strand, test). The prose outside the markers is written by hand.

How to read the numbers:
- A reference is one `use` leaf (`use mod_api::{A, B}` is two) or one qualified path outside `use`. Comments and
  strings don't count.
- Test code (tests/, examples/, `*_tests.rs`, `#[cfg(test)]` and `#[test]` items, modules declared under them) is
  counted apart: the layer rule ignores dev-dependencies, but a move still has to carry it.
- "To make public" and "inbound" resolve names textually (no compiler), so they are estimates: a method named like
  a private engine function counts as one.
- Strands come from the `RULES` table in the scanner, the first matching pattern winning; correct a strand there.

## Strands and their proposals

**Loading (phase 1): move.** `mod_list.rs`, package reading (`horizon-mod-package`), the wasm start
(`horizon-mod-wasm`) and the dependency order go to `horizon-mod-host`. `entry::main_with` mixes them with engine
startup and takes `ModEntry`, `NativeSlot` and `BuiltMod`: it splits into an engine start that takes what the host
loaded through one registration call, and the host's load step that runs before it. The engine keeps one start call.

**Host (phase 2): not built.** The generated `Host` impls forward each of the 899 host trait methods to an inherent
`Game` function in the hook-body files, which stay in the engine. Under option B the `Host` traits are engine-layer
vocabulary, so the engine implements its own interface, which the layer rule allows. A socket would move only the
forwarders and `mod_api_host.rs` (under 1,000 lines). It would make the 899 functions public, and engine unit tests
couldn't use a host implemented above the engine: a dev-dependency cycle gives the test build a different `Game`.
The engine↔`mod_api` value conversions (`game/modding/api_values`) are counted with the hook bodies: 117 engine
files that stay use them.

**Slots (phase 3): socket.** Eight production references: `entry.rs` (`mod_points::register`, `SlotListener`,
`PointId`), `game.rs` (`seal`), `build.rs` and the `include!`s of generator output. The engine owns the slot table
and the "anyone listening?" check; module discovery (`game_modules.rs`, `.game-area` markers) moves to a small engine
crate both trees share, as agreed with upstream on #2534; `horizon-mod-api-gen` calls it.

**Attachments (phase 4): socket.** One opaque extension field the engine stores and carries across saves, moves and
transfers; `AttachmentLifetime` becomes the host's use of it. `horizon-world`'s dependency on `horizon-mod-runtime`
had no use in code and is removed in phase 0. `horizon-protocol` uses `attachments::{AttachmentSync, Holder}` in one
file.

**Content and render (phase 5): sockets.** The engine asks for additions to its registries at load and the host
answers; the renderer gets sockets for extra models and layers. `horizon-client-render` has five mod dependencies
(`-mod-api`, `-mod-api-macros`, `-mod-package`, `-mod-render`, `-mod-runtime`).

**Hooks (phase 6): waits.** The hook bodies under `game/native_hooks/` and most of `game/modding/` are `impl Game`
blocks, which can't leave the crate as written. Whether they move at all depends on upstream's answer about keeping
the mod API's vocabulary in a crate below the engine (#2534); nothing in this strand moves until then.

## What a script can do

- Phases 1 and 3: a move map (file → destination) is mechanical once each moved file's production references from
  files that stay in the engine are handled, and its unit tests have a home: every phase PR lists both. The
  accessors `Game` grows are listed by the scan ("to make public") and named by hand.
- Phase 6, if it happens: sockets generated from the hook catalog.
- Hand design: the attachment field (phase 4), the registry and render sockets (phase 5), and the vocabulary split.

## The mod API's engine vocabulary

`horizon-mod-vocab` is the engine-owned interface crate for #2534 option B. It holds events, `HookId`, `Hooks`,
Host traits, plain values, and `runtime.rs` dispatch. `horizon-mod-api` re-exports that surface without changing
mod-facing paths and owns the WebAssembly guest transport. `horizon-mod-api-macros`, `horizon-mod-point-shape`,
and `horizon-mod-api-gen` are engine crates too. The launcher reaches the latter two through the platform's
optional `mod-build` facade, not through new layer exceptions.

The extraction's compile established that the dispatch closure is larger than plain vocabulary:

- `runtime.rs` enters native crash markers; their guard owns a profiler guard. Crash markers and the profiler
  therefore move with dispatch. Six profiler pool operations retain their existing `unsafe` implementation.
- Wire's Writer and Reader own resource encode/decode operations. The resource codec moves with them, including
  `ResourceScope::native_root`. Guest imports, arenas and generated guest calls stay in `horizon-mod-api`.
- `Hooks::register` names `RegistrationContext`; handle methods also read phase and registry-key state. Their
  types, access checks, installed registry-key tables and supporting reload contracts stay together initially.
- Parts dispatch calls `has_part_hook`, `parts` and `entered_parts`. Its tables must be below the engine.
  Registration does not separate by pure moves: generated `parts_modules.rs` joins the Registrar supertrait,
  area traits and blanket implementations, while hand-written areas contain inherent implementations on
  `dyn Registrar` and `HookParts`. The registrar and registry-key resolution closure move with the tables.
  Test helpers stay beside the private tables and remain available through `mod_api::testing`.

This is **not an unsafe-free or stateless interface**. The crate denies new unsafe code, with reasoned local
allowances at the carried sites. [#2587](https://github.com/arismoko/horizon/issues/2587) separates crash marks,
profiling and resource access behind engine-owned hook points and adds the generated installation interface
needed to move Parts registration above the engine.

The next dependency-switch PR changes engine dependencies to `horizon-mod-vocab` and removes their old allowed
rows. It does not move hook bodies. The generated tables below still show the current engine dependency names;
all production engine uses of `mod_api` now name vocabulary definitions or their re-exports, not guest transport.
